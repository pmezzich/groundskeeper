## (1) What the methodology SURFACED that a naive read would miss

A naive read of #1411 says: "tiny good-first-issue — make `list_creative_formats` not fabricate a local entry for a foreign `agent_url`, wire the BDD step, flip xfail→pass on 4 transports." Running the phases refuted or complicated almost every load-bearing premise:

- **The "MUST NOT fabricate" requirement is already satisfied — there is no production change to make there (Phase 0.2).** `creative_formats.py` has **zero** fabrication code paths (`grep` for `fabricat|create.*Format(` returns nothing). The `format_ids` filter at `src/core/tools/creative_formats.py:269-274` only *narrows* the existing format list (`formats = [f for f in formats if f.format_id.id in format_ids_set]`); a foreign format_id simply matches nothing and drops out. So the headline DoD item is a no-op against current code — the real work is test-side.

- **DECISIVE BLOCKER the issue hides — "all 4 transports" is structurally impossible on REST (Phases 2.2 + 6).** The scenario's When-step must send a `format_ids` filter, but the REST endpoint **drops every filter param**: `tests/harness/creative_formats.py:97 build_rest_body()` returns `{}` intentionally because `ListCreativeFormatsBody` in `src/routes/api_v1.py` declares only `adcp_version`. Consequently **every** filter-using UC-005 scenario is already hard-xfailed on REST in `_REST_XFAIL_TAGS` (`tests/bdd/conftest.py:339-357`, `strict=True`). The third-party scenario cannot "flip xfail→pass across all 4 transports" without **first fixing the REST endpoint to forward `format_ids`** — a separate production change and merge-order dependency the issue never mentions. A naive implementer would wire the steps, watch REST XPASS-fail or stay xfailed, and be stuck. This alone justifies the skill.

- **The central noun "observation" has no representation in the code or the response model (Phase 4.1 hidden decision).** `ListCreativeFormatsResponse` carries `errors: list[Error] | None`, `status: TaskStatus`, `source`, `governance_context` — but nothing modeling "observation vs graded failure." `grep -ri observation|on_out_of_scope|graded src/` finds nothing relevant. "Observation/`on_out_of_scope=warn`" is a *compliance-runner* concept from `media-buy/index.yaml list_formats_integrity`, not a seller-response field. So "report as an observation" cannot be a production assertion — it can only mean *the seller returns an empty `formats[]` (no fabrication) and the BDD Then-step treats empty-for-foreign-agent as a non-failure*. That is a genuine design fork the issue glosses, exactly as the skill's Phase 4.1 predicts.

- **The filter ignores `agent_url` entirely (latent correctness gap, Phase 0.2 trace).** Line 272 keys only on `fmt.id` (`{fmt.id for fmt in req.format_ids}`), discarding `agent_url`. Two formats with the same `id` but different `agent_url` would collide. If the test is to *prove* foreign references don't match local formats, this is the line under test — and it would need to compare on `(agent_url, id)`, not `id` alone. A naive read wouldn't notice the filter is agent_url-blind.

- **Spec-pin dependency is real and now satisfied (Phase 0.1).** `agent_url` is a **required** field on `FormatReferenceStructuredObject`/`FormatId` on the installed pin (`adcp==5.7.0` / spec `3.1.0-beta.3`, re-derived from the package, not the issue prose) — a declared contract, not an `extra="allow"` passthrough. The issue says "cleanest after PR #1399 (adcp==5.7.0) lands"; #1399 **merged today (2026-06-16 12:51 UTC)** and itself touched `creative_formats.py` + `api_v1.py` + `format.py`, so the coupling was genuine. The prerequisite is cleared — but the local branch is `fix/update-media-buy-not-found`, so a base/rebase check (Phase 6.0) is warranted before assuming #1399 is in the working base.

- **"Wire the BDD step" means net-new step code, not a test-pin (Phases 1.1/3.1).** The `uc005_creative_formats.py` domain module is intentionally empty (6 lines); none of the three storyboard scenarios' Given/When/Then strings resolve to any step def. But strong reuse exists: `generic/when_request.py:181 when_request_format_ids` already dispatches `format_ids` filters, and `uc006_sync_creatives.py:1809/1839` has near-identical foreign/unreachable-`agent_url` Givens (registry mock → `get_format=None`, `{id, agent_url}` payload) to mirror. **#1452** (open) is a live precedent: it added 85 lines to wire one previously-xfailed scenario — confirming scope, refuting "trivial."

## (3) GAPS the held-out issue exposed in the skill

Two real gaps, one minor:

- **GAP A (missing check): no "transport-capability parity" check — the skill assumes all 4 transports *can* express the scenario.** Phase 2.2 covers the xfail *registry* and strict-xpass, and Phase 2.1 covers whether one harness supports a *multi-operation flow*, but **nothing checks whether a given transport can even carry the request shape the scenario needs.** Here, REST structurally drops `format_ids` (`build_rest_body → {}`, `ListCreativeFormatsBody` has no filter fields), so "flips xfail→pass across all 4 transports" is false on REST regardless of how the steps are written — and the skill has no HOW step that would have forced me to open `build_rest_body`/the REST route and diff the request fields against what the scenario sends. This is the single most important finding and the skill currently surfaces it only incidentally (via the `_REST_XFAIL_TAGS` grep in 2.2), not as a first-class check. **Proposed fix:** add Phase 2.3 "Per-transport request-shape parity — for each filter/param the scenario's When-step sends, confirm the REST `build_rest_body` and the route Body model actually forward it; a dropped param means that transport's DoD line is a separate production fix, not a test-pin." Pair it with a red flag: "DoD says 'all 4 transports' but the param is in `_REST_XFAIL_TAGS` / `build_rest_body` returns `{}`."

- **GAP B (a HOW step that didn't fully work): Phase 4.1's "schema authority / response field" fork assumes the asserted concept is *representable* in a model.** The skill's forks (seeding strategy, schema authority, transport set, harness depth) presume the thing under test is a field/shape you can round-trip via `model_validate`. #1411's load-bearing noun ("observation vs graded failure") is a **process/grading-runner concept with no model field at all** — `grep` for it across `src/` and the response model returns nothing. The skill has no HOW step that says "if the issue's key verb/noun has no field on the pinned response model, the requirement is a *test-grading* semantic, not a production contract — resolve it as a BDD-assertion convention, not a schema change." I had to derive that myself; the skill nudged toward it (Phase 4.1's "schema authority when no `*.json` ships") but didn't name the "concept exists only in the compliance runner, not the SDK" case. **Proposed fix:** extend Phase 0.2 or 4.1 with an explicit "term-grounding" sub-check: for each load-bearing noun/verb in the DoD, confirm it maps to a model field, an exception class, or an enum on the pin; if it maps to none, classify it as a test-harness/grading semantic and plan the BDD assertion accordingly.

- **Minor (HOW friction, not a logic gap):** several `grep`/`python -c` HOW snippets assume `$PY` is exported in the same shell line; on this Windows/Git-Bash setup a stray `"$PY=..."` mis-assignment silently broke one command, and the unicode in the repo path corrupted the `Read` tool (had to fall back to Bash). Not a methodology gap, but the skill's Environment block could note "assign `PY` once per command block; avoid `Read` on paths with non-ASCII and use `python -c` to print file slices." The skill's `PYTHONUTF8=1` guidance was correct and necessary.

**Net:** The skill is sound and caught the issue's buried REST blocker and the missing-model "observation" fork — the two things that would sink a naive implementation. The held-out issue exposed one genuinely missing check (per-transport request-shape parity) and one under-specified fork case (asserted concept absent from the pinned model). Both are concrete, additive fixes that would make the skill strictly better.
